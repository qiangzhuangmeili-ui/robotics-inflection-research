# 第一轮：基础资料批量收集，结束后集中补缺

本规则于2026-10-26根据用户指示加入。先广泛收集可复用资料，再用指标一轮轮收紧，最后少量公司深读。采集日期与研究截止日分开；本轮沿用当前PROJECT_STATE.json的knowledge_as_of，不因今天采集就混入截止日之后公告。

“应收尽收”以这份有边界的资料清单为准，不要求抓取所有无关日常公告。全池核心报告理论上最多1054×6=6324个文件槽，实际须扣除上市前、不适用和未披露；文件槽不是应有PDF的事实数量。先统计大小与已有命中，再低并发分批下载，原件存Drive，GitHub只存索引、进度与缺口。无须AI逐份精读这些原文。

## 先自动跑一整轮，再交给人工

1. 先盘点Drive、现有document_registry和本机缓存。同一份原文按官方公告ID、真实Drive file ID和SHA256复用；不覆盖现有业务研究成果。
2. 用10个公司/不同市场做采集格式校准，只验证接口、证券主体、报告期、全文/摘要、字段与存储，不开展业务深读；通过后按data/intake_batch_index.csv跑11个技术批次，每批最多100家公司。技术批次不是100家深研任务。
3. 一家失败先记自动队列，继续其他公司。单次超时后有限重试、换官方来源；源站普遍失败时暂停该来源并保留断点，不对1054家公司重复撞同一错误。
4. 处理完整候选池及计划槽位后，合并缺口。尚未披露、不适用、部分已取得、访问失败、字段未披露分别记录；不能把“尚未自动尝试”直接推给用户。
5. 只给用户一份整轮补缺总表，按网站/软件、报告期和可共同下载的批次分组。写清缺哪些文件/字段、尝试过什么、一次怎样导出、放到哪个本地/Drive目录。使用templates/整轮采集人工补缺.csv，不每完成一家就发一次补件请求。
6. 用户统一补交后，按文件ID/哈希自动核销缺口，再开始指标宽筛→收紧→少量公告核验。后续新发生的公告或只有重点公司才需要的特殊证据，可另开增量批次；不能承诺以后绝不需要新资料。

## 收集和核验的状态分开

发现链接、已下载、已归档Drive、可读且主体/报告期匹配、业务证据已核实是不同状态。首轮只验文件和数据可用性；不要求每条关键断言做页码摘录才算“收到了资料”。之后采用业务结论时仍按原证据规则核读原句和物理页，不放宽标准。

资料缺失不等于公司没有业务，不能填0或自动淘汰。北交所、近期上市、历史代码变更公司单列处理，不能沿用只支持沪深的旧15只批量入口当全市场已覆盖。
